# 开岗扫描执行方法

一次扫描 = 对给定公司集合逐家判断"是否有新开放的目标岗位",输出结构化结果。即时扫描(用户在场)和定时扫描(scheduled task 里跑)都用这套方法。

---

## 一 · 扫描输入

- **公司集合**:来自用户的推送范围选择(全部两大类 / 只推荐方向相关公司),渠道地址见 [channels.md](channels.md)
- **岗位类型**:实习 / 校招 / 都要(来自用户届次判断)
- **方向关键词**:来自方向评估(见 direction-map.md 的关键词映射);用户选"全部设计岗"则用宽关键词:设计、HMI、UX、UI、交互、视觉、3D、体验
- **城市偏好**:有则用于排序和标注,不做硬过滤(异地机会照报,标注 base)
- **时间窗口**:见下文"新开岗判定"

## 二 · 逐家检查策略

对每家公司,按成本从低到高:

1. **WebFetch 官方入口**(channels.md 中的校招/实习 URL),prompt 里明确要找:是否有匹配关键词的在招岗位、岗位名、城市、发布/截止时间。
2. 官方入口是 JS 渲染抓不到列表(很常见,channels.md 有标注)或访问失败 → **WebSearch 兜底**,按 channels.md 第七节的渠道顺序:
   - `site:nowcoder.com 公司名 设计 校招` / `公司名 HMI 实习 2027届`
   - `site:shixiseng.com 公司名 设计`
   - `公司名 校园招聘 2027届 就业网`(国央企必发高校就业网)
   - `公司公众号名 校招 开启`
3. 搜到的结果必须核对时效:带年份/届次的标题优先,2 年前的结果直接丢弃。

效率约束:单家公司最多 3 次尝试(1 fetch + 2 search),查不到就标"未能确认",不要陷进去。一次扫描 20-40 家公司,总时间应控制在合理范围,能并行就并行(有 Agent/子任务能力时,按分类分组并发查)。

## 三 · "新开岗"判定

定时扫描的新会话没有上次扫描的记忆,不能靠对比历史列表判断"新"。用**发布时间窗口**代替:

| 扫描频率 | 报告窗口 |
|---|---|
| 每天 | 发布时间在 48 小时内 |
| 每周一三五 | 发布时间在 4 天内 |
| 每周一次 | 发布时间在 8 天内 |

判定规则:

- 岗位/简章带发布日期且在窗口内 → **新开岗**,进推送主体
- 在招但无法确定发布时间 → 单独归入"在招但发布时间未知"区,只在首次扫描或用户即时扫描时全量列出;定时推送里只挑与用户方向高匹配的提 1-2 条,避免每次推送重复同样的存量岗位
- 简章/岗位标注了**投递截止时间且在 7 天内** → 无论发布时间,都进推送并标 ⏰ 截止提醒——这正是这个工具存在的理由(学生经常在 HC 快关时才知道)

## 四 · 输出格式

### 即时扫描(用户在场)

按匹配度分组输出,每条:

```
**公司 · 岗位名**(实习/校招 | 城市 | OEM-新势力/供应商-国内…)
一句话:为什么和你的方向匹配(或不完全匹配但值得看)
投递入口:URL
发布:X月X日 / 未知 | 截止:X月X日 / 未标注
```

结尾给一段"本次扫描说明":查了几家、几家确认在招、几家未能确认(列名字),让用户对覆盖面有预期。

### 定时推送(scheduled task 里)

推送消息要能在手机通知里被快速消化,结构:

```
🚗 开岗雷达 X月X日

【新开岗 N 个】
1. 公司 · 岗位(城市)— 截止X月X日 → 链接
2. …

【⏰ 即将截止】
- 公司 · 岗位 — X月X日截止

【窗口提醒】(只在窗口切换时出现,如"9月中,秋招 HC 释放高峰,本周投递优先级最高")
```

没有新开岗时发一条简短确认("今日扫描 X 家,无新开岗;当前在招存量 Y 个未变"),让用户知道系统在工作,而非静默——静默会让用户怀疑监测挂了。

## 五 · 诚实性约束

- 检测不到 ≠ 没开岗。官方站抓取失败又搜不到时,如实标"未能确认",不要写成"未开放"。
- 不虚构岗位、发布时间、截止时间。搜索结果里没有的信息标"未标注"。
- 二手信息(牛客帖子、小红书)标注来源性质,提醒用户以官方入口为准。
